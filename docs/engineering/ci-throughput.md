# CI throughput work

Keep GitHub-hosted runners. The [Boardy CI article](https://x.com/owengretzinger/status/2116291924219060319) is a source of experiments, not an AutoGPT benchmark. Its paid runners and larger machines are outside this work's scope. No tests are deleted to meet a duration target.

## Affected platform projects

`platform-ci.yml` selects backend, frontend and full-stack suites for PR and merge-group changes. The existing suite workflows remain independently dispatchable and run in full every night on the repository's default branch, currently `master`. Their existing `dev`/`master` push triggers also remain.

The selector uses `.github/ci-projects.json`. A frontend change runs frontend and full-stack checks; a backend or shared-library change runs backend and full-stack checks. Prisma schema, backend container, integration catalog and compose changes preserve their cross-project dependencies. Unknown platform directories, CI configuration and other unclassified files select every suite. Documentation, classic and issue-template changes do not select platform suites; their own workflows remain responsible for them.

PR selection compares the merge base with the PR head. Merge groups compare their base and head commits. Checkouts that read history use a full, blobless fetch. Deleted paths and both sides of renames are included. Missing revisions and unsupported event types fail instead of returning an empty plan.

The safety check separately reads Git's diff and applies a conservative policy that does not consult the selector's graph or file list. The final job repeats this check and requires every selected suite to succeed. A missing, cancelled or skipped selected suite fails. The CLI tests deliberately remove a backend change from the graph, produce an empty selection, supply successful selection plus skipped suite results, and require rejection. They also cover renames, deletions, base-only changes, schema dependencies, failed selection and nightly/full dispatches.

This is project selection, not individual test selection. The full backend matrix and all sixteen frontend shards still execute whenever their project is affected. The existing advisory journeys policy is preserved; smoke, API types and all required tests still block.

## Five-minute target: pending hosted validation

The last fully passing baseline, [run `41578935067` on `797627a`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41578935067), took 18 m 34 s. Its smoke job took 17 m 31 s, including an 8 m 46 s frontend image build. The slowest backend and frontend jobs took 14 m 47 s and 11 m 42 s. The separate AMD64 appliance build/smoke/scan job took 18 m 38 s, and the required PR-status job took 18 m 47 s. Overlapping job times must not be added.

The next candidate splits backend files within their existing fixture groups into 31 partitions per Python and frontend integration tests into sixteen isolated shards. Coverage upload counts and required artifact gates expand with the matrices. No test files or assertions are removed.

Both Docker frontend build paths use `next build --turbopack`, supported by the installed Next 15.5 release. The obsolete Webpack cache mount and its restore/import/export/save steps are removed. Docker layer and dependency caches remain. The appliance vulnerability scan now scans vulnerabilities only; the separate high/critical secret scan retains its previous scope and failure gate. This avoids scanning secrets twice.

These changes need complete hosted builds, source-map coverage, test inventories, appliance lifecycle tests and final status validation before a speedup can be claimed. Measure trigger-to-green time, including scheduling and setup, against the baseline. More shards may increase scheduling delay, and appliance startup/restart remains a separate cost. Five-minute CI and merge-queue performance are not yet established.

## Hosted frontend comparison

`frontend-tool-benchmark.yml` runs comparisons by manual dispatch. It uses the selected ref's SHA, the existing pnpm lock, Node 24.22.1 and standard GitHub-hosted runners. Trusted dev/master pushes still seed the experimental dependency cache. Diagnostic comparisons do not run on PR updates: GitHub's PR path filter sees the entire PR diff, so it repeated every experiment on unrelated follow-up commits. Candidate tools live in a temporary directory, without changing the project lock or installed TypeScript used by Next.js.

- Compare existing Next/ESLint plus custom Oxlint checks with Oxlint 1.90.0 and a migrated configuration. Preserve the current custom plugins and overrides in the migration input. Retain all warnings about unsupported rules. Inject invalid keyboard handling, conditional hooks and props mutation in a compiler-enabled directory, and require both linters to report the intended rule before considering a replacement. Passing these probes alone does not prove every rule has equivalent semantics.
- Compare TypeScript 5.9 with TypeScript 7.0.2 and Bun 1.4.4. Extend the existing configuration with the original implicit type packages and side-effect-import default, and normalize relative paths for the newer compilers. Retain the effective configuration and all diagnostics. Every checker must detect an injected assignment error in a project source file. The required API-schema job now uses Bun with this same compatibility configuration; the schema export and comparison remain required. The package's TypeScript version and local `pnpm types` stay unchanged.
- Compare Prettier with Oxfmt 0.75.0, using its configuration migrator, including the Tailwind plugin settings. Retain migration warnings and formatting differences; never rewrite application files during the benchmark.
- Run each Vitest shard twice on one machine, with isolation enabled and disabled. Keep the forks pool, CPU-based worker limit, coverage and test configuration identical; disable the result cache and alternate ordering across shards. Retain JUnit and Cobertura for both layouts, and require identical passing test inventories. No coverage is sent to Codecov from diagnostic runs. Shared workers are not adopted until repeated and reordered runs validate state cleanup.
- Time installation from the existing pnpm store cache, then separately time restoring installed `node_modules`. Key the experiment by OS, architecture, runner image family, exact Node version and dependency configuration. Trusted `dev` and `master` pushes seed this cache when dependency inputs change. Production jobs continue using their existing dependency setup until restore benefit and cache scope are demonstrated.

Artifacts record commands, exit statuses, durations, lock/source hashes, runner hardware, negative probes and compatibility logs. Setup and final diffs distinguish generated files changed by dependency installation (such as MSW's browser worker) from changes introduced during measurement. A missing candidate executable is recorded without preventing the other comparisons. A diagnostic workflow succeeding means its measurements were collected, not that a candidate passed. Compare whole-job and queue durations from Actions as well as command times. Repeat close results before adoption, and distinguish a faster tool from a faster PR critical path.

References: [Oxlint migration](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html), [Bun type checking](https://bun.sh/docs/runtime/check), [Vitest isolation](https://vitest.dev/guide/improving-performance.html), [Oxfmt migration](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier.html), [GitHub cache scopes](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Backend comparisons are documented in [backend-ci-sharding.md](backend-ci-sharding.md).

## Latest completed measurements

The paired [frontend comparison on `37668f0`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41570897670) measured TypeScript 5 at 33.42 s, TypeScript 7 at 10.85 s and Bun at 1.77 s on one standard runner. All three passed the project and rejected the injected type error. This repeats the previous successful candidate comparison; it is a component speedup, not a whole-PR duration. The [required Bun step on `ef8289c`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41574769692/job/125715733320) passed with a freshly exported backend schema; checking including configuration preparation took 5 s.

Shared-worker execution failed all four shards again while the isolated runs passed, so isolation stays enabled. Oxfmt took 1.33 s but disagreed with Prettier on 52 files; it is not adopted. The installed-dependency cache restored in 11.49 s versus an 18.73 s install, which does not establish a production cache-hit rate. Oxlint migration resolves Next.js's transitive plugin, but the [result on `ef8289c`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41574769762/job/125715607820) produces an invalid configuration and drops `no-restricted-syntax`, which enforces keyboard safety. ESLint stays authoritative. The compiler mutation probe also needs correction because ESLint did not reject it; it provides no parity evidence.

The [platform run on `37668f0`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41570897770) completed in 18 m 49 s with all required suites passing. Four advisory journeys failed solely because the published changelog returned 502. The base-branch status checker did not yet recognize the nested advisory job name, so it failed too; the branch contains the name-policy fix, but trusted base code will only pick it up after merge.

Local full-stack CI explicitly supplies a checked-in changelog index through the existing popup fixture. This removes a publishing-site dependency from unrelated journeys and still marks the release as seen. The option rejects non-loopback apps; preview journeys continue to forward live responses, including failures. API route tests still check upstream failures, and the journey error guard has no new exceptions.

## Test-runner console teardown

On `37908fc`, frontend shard 2 passed every test but failed when Vitest closed its worker RPC with `onUserConsoleLog` still pending. This matches [Vitest issue 11153](https://github.com/vitest-dev/vitest/issues/11153); its [upstream fix](https://github.com/vitest-dev/vitest/pull/11619) is not present in the published Vitest 4.1.11 or 4.1.12 console implementation.

CI uses the documented [`disableConsoleIntercept`](https://v4.vitest.dev/config/disableconsoleintercept) option to write console output directly. The tradeoff is losing per-test log prefixes in CI, while output remains visible. Local logging retains its usual formatting. Isolation, test assertions, unhandled-error checks and coverage gates stay enabled. Before shard 1 runs, a small hosted probe uses the real project configuration to require visible stdout/stderr and a nonzero exit for an intentional unhandled rejection. It removes its temporary test before the real suite runs.

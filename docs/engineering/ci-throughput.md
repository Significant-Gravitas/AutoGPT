# CI throughput work

Keep GitHub-hosted runners. The [Boardy CI article](https://x.com/owengretzinger/status/2116291924219060319) is a source of experiments, not an AutoGPT benchmark. Its paid runners and larger machines are outside this work's scope. No tests are deleted to meet a duration target.

## Affected platform projects

`platform-ci.yml` selects backend, frontend and full-stack suites for PR and merge-group changes. The existing suite workflows remain independently dispatchable and run in full every night on the repository's default branch, currently `master`. Their existing `dev`/`master` push triggers also remain.

The selector uses `.github/ci-projects.json`. A frontend change runs frontend and full-stack checks; a backend or shared-library change runs backend and full-stack checks. Prisma schema, backend container, integration catalog and compose changes preserve their cross-project dependencies. Unknown platform directories, CI configuration and other unclassified files select every suite. Documentation, classic and issue-template changes do not select platform suites; their own workflows remain responsible for them.

PR selection compares the merge base with the PR head. Merge groups compare their base and head commits. Checkouts that read history use a full, blobless fetch. Deleted paths and both sides of renames are included. Missing revisions and unsupported event types fail instead of returning an empty plan.

The safety check separately reads Git's diff and applies a conservative policy that does not consult the selector's graph or file list. The final job repeats this check and requires every selected suite to succeed. A missing, cancelled or skipped selected suite fails. The CLI tests deliberately remove a backend change from the graph, produce an empty selection, supply successful selection plus skipped suite results, and require rejection. They also cover renames, deletions, base-only changes, schema dependencies, failed selection and nightly/full dispatches.

This is project selection, not individual test selection. The full backend matrix and all sixteen frontend shards still execute whenever their project is affected. The existing advisory journeys policy is preserved; smoke, API types and all required tests still block.

## Hosted frontend comparison

`frontend-tool-benchmark.yml` runs comparisons by manual dispatch. It uses the selected ref's SHA, the existing pnpm lock, Node 24.22.1 and standard GitHub-hosted runners. Trusted dev/master pushes still seed the experimental dependency cache. Diagnostic comparisons do not run on PR updates: GitHub's PR path filter sees the entire PR diff, so it repeated every experiment on unrelated follow-up commits. Candidate tools live in a temporary directory, without changing the project lock or installed TypeScript used by Next.js.

Dispatch with `benchmark=builds` to compare Webpack and Turbopack separately from the tool/worker experiments. Each runner builds both compilers cold, with unchanged source and retained compiler cache, and after editing one imported source file. A second runner reverses compiler order. Each rebuild removes all output except `.next/cache`; the source edit is restored even if a build fails. Commands use the same generated client, VAD assets, browser source maps, Playwright flags and 8 GB heap cap as the full-stack Docker build. Missing standalone output, missing browser source maps, missing builds or different route inventories fail the comparison. These structural checks do not replace runtime or coverage validation, and compiler-command time excludes Docker export, setup, tests and queueing.

The [paired build comparison on `eb1fd39`](https://github.com/Significant-Gravitas/AutoGPT/actions/runs/41646244199) passed all twelve builds and output checks on two standard four-vCPU AMD EPYC 7763 runners. Observed command-time ranges were:

| -------------------------------------- | --------------- | --------------- |
| Cold                                   | 168.34–174.38 s | 285.99–295.00 s |
| Unchanged source, cache retained       | 171.05–177.77 s | 122.35–125.40 s |
| Imported source edited, cache retained | 170.71–174.06 s | 131.23–135.67 s |

These measurements do not establish complete CI duration or runtime equivalence between compilers.

## Test-runner console teardown

On `37908fc`, frontend shard 2 passed every test but failed when Vitest closed its worker RPC with `onUserConsoleLog` still pending. This matches [Vitest issue 11153](https://github.com/vitest-dev/vitest/issues/11153); its [upstream fix](https://github.com/vitest-dev/vitest/pull/11619) is not present in the published Vitest 4.1.11 or 4.1.12 console implementation.

CI uses the documented [`disableConsoleIntercept`](https://v4.vitest.dev/config/disableconsoleintercept) option to write console output directly. The tradeoff is losing per-test log prefixes in CI, while output remains visible. Local logging retains its usual formatting. Isolation, test assertions, unhandled-error checks and coverage gates stay enabled. Before shard 1 runs, a small hosted probe uses the real project configuration to require visible stdout/stderr and a nonzero exit for an intentional unhandled rejection. It removes its temporary test before the real suite runs.

# Hosted MCP Catalog

The MCP catalog helps users connect official remote services from **Settings → Integrations**. It includes public documentation and research tools, account integrations, and services that require a tenant or regional URL. Native integrations remain separate choices with their own supported blocks and credentials.

This guide describes the catalog implementation and its **2026-09-12** support snapshot: **85 records**, of which **58 are offered on a hosted AutoGPT deployment**. An additional AWS Core connection is offered when the AutoGPT frontend uses a localhost callback. The remaining 26 records are retained as unavailable inventory and are hidden from connection choices.

“Offered” means the documented remote transport and authentication fit the current connector. It does not mean every account, plan, permission, or tool has been tested. Use the per-service evidence below when assessing readiness.

## Source of truth and visibility

The source is [`mcp_catalog.json`](../../../autogpt_platform/backend/backend/integrations/mcp_catalog.json); [`mcp_catalog.py`](../../../autogpt_platform/backend/backend/integrations/mcp_catalog.py) validates it and applies runtime visibility rules. Provider metadata, connection choices, and the MCP guide use the filtered catalog.

| Field | Maintainer convention |
| --- | --- |
| `name`, `display_name`, `description` | Keep a stable unique `mcp_...` ID. Describe the actual server's purpose, including whether it exposes public documentation, account data, sandbox tools, or a gateway. A shared brand does not imply equivalent capabilities. |
| `official`, `documentation_url` | Require vendor documentation or a vendor-owned repository that establishes both the server and its authentication contract. A marketplace listing alone is insufficient. Link directly to setup instructions. |
| `connection_mode` | `hosted` has one fixed endpoint. `custom` requires a user-selected region, tenant, deployment, or product URL. `unavailable` retains research without offering a connection. Only `hosted` may have a non-null `server_url`. |
| `server_url`, `server_url_options` | Use canonical public HTTPS endpoints. Provide labeled regional choices when documented. Do not put a placeholder tenant, secret, query parameter, or fragment in the catalog. URL validation also rejects IP hosts, local/internal hostnames, nonstandard ports, and embedded credentials. |
| `auth_methods`, `auth_mode` | List only supported methods: `oauth`, `bearer`, `basic`, or `none`. Order determines the initial choice. `auth_mode` must match the first method (`token` for Bearer or Basic). Unavailable entries have no methods. |
| `oauth_server_url` | Use only when the vendor has a distinct OAuth endpoint, as with Parallel Search and Context7. It must represent the same intended service. |
| `oauth_scopes` | Set explicit documented default scopes when the provider supports a meaningful subset. `[]` requests no scopes; omission/null permits discovery defaults. An advertised scope list is not evidence that every scope is required or read-only. |
| `oauth_write_scopes` | Add documented optional permissions, disjoint from explicit defaults. These are requested only after the user selects **Allow changes**. Explain the actual effect; Treg's optional grant enables tool execution, including reads, rather than just writes. |
| `oauth_callback_mode` | `loopback` restricts OAuth to a frontend hostname of `localhost`, `127.0.0.1`, or `::1`. Hosted deployments remove this method; a documented token alternative remains available. Without an alternative, the entry is hidden. |
| `setup_instructions` | State required plan, admin/client approval, API-key type, region, tenant, scopes, and external token-renewal requirements. Keep instructions specific enough to act on. |

The current connector uses remote HTTP. It cannot launch local stdio processes, supply arbitrary authentication headers, configure a vendor's fixed OAuth client ID and secret, or complete tenant app registration for the user. Such requirements must not be presented as working presets. Self-hosting AutoGPT does not add stdio support.

OAuth uses discovery and dynamic client registration (DCR), with the advertised `none`, `client_secret_basic`, or `client_secret_post` client authentication and PKCE. Registration, consent, and tool access are separate stages. A vendor can accept registration while still requiring an administrator to approve the client or user at consent time.

For known catalog URLs, the OAuth route applies the deployment's catalog policy and uses configured scopes when the caller omits them. Regional and alternate OAuth URLs participate in the same lookup. Credentials retain provider identity `mcp` and are associated with the user and server URL; the branded catalog ID is not a separate credential provider.

## Choosing endpoints and permissions

Prefer a fixed endpoint only when it is valid for the intended account population. Use `custom` for tenant URLs and region selectors instead of guessing a user's region. Keep distinct products separate: Airwallex Developer targets sandbox development, Airwallex AgentOS targets production account workflows, AWS Knowledge provides public documentation, and Plaid Dashboard provides developer diagnostics rather than personal bank aggregation.

Offer manual Bearer or Basic authentication only when documented for that endpoint. Some keys need special restrictions: Brevo requires an MCP-enabled key, Coda requires an MCP-restricted token, and Langfuse requires a public/secret key pair encoded for Basic authentication. A standard API key is not interchangeable with these credentials.

The initial OAuth grant is not universally read-only. Some vendors enforce access through roles, selected resources, or their consent screen instead of documented OAuth subsets. For example, Amplitude's **Use MCP (read)** and **Use MCP (write)** project permissions control tool access. Appwrite and Bird require users to review the provider's requested account permissions. Do not label such connections read-only without evidence.

These explicit permission choices were checked separately. Both the default bundle and the optional bundle were accepted in hosted registration requests; this does not prove the resulting account tools work.

## Verification snapshot: 2026-09-12

The checks used the actual AutoGPT MCP client and registration code in development. They are not deployment validation. No vendor test accounts or credentials were available, so **account consent, authorization-code exchange, authenticated account reads, token refresh, and revocation were not tested for any service**.

- **Public read passed** means initialization, tool listing, and one named anonymous documentation/data read returned a useful result. It does not verify every listed tool or any account action.
- **Registration accepted** means the vendor accepted client registration for a hosted callback and the returned metadata passed client model validation. The final default preflight covered 42 distinct OAuth URLs across 41 services, including both Amplitude regions. The seven optional permission bundles were also checked separately.
- **401 challenge** confirms the endpoint requires authentication. It does not verify credentials, account access, or tool listing.
- **Endpoint required; not probed** means setup is documented, but no user-specific deployment, tenant, or selected product endpoint was available for a live check.
- Hidden records have no supported account connection verified by these checks. Documentation review and diagnostic failures are identified separately.

Live probes negotiated both modern and legacy MCP protocol versions. Tool discovery alone is insufficient: inspect the result of a benign call for semantic errors even when JSON-RPC returns successfully.

## Adding or revising a service

1. Verify the official server, purpose, canonical URL, transport, authentication format, scopes, and prerequisites in current vendor documentation. Preserve useful aliases in the description when names change, but do not merge different products because they share a brand.
2. Choose a mode and authentication methods that the current connector can execute. Check tenant, region, production/sandbox, and callback restrictions. Retain unsupported services as unavailable inventory rather than presenting a speculative connection.
3. Probe initialization and tool listing with the actual client. For public services, inspect schemas before choosing one cheap, benign read. Check returned content for semantic errors. Do not use payments, writes, account actions, or paid tool execution as anonymous smoke tests.
4. For OAuth, validate discovery, issuer identity, supported client authentication, and registration against the deployment's callback. Check default and optional scopes separately. Registration is a client-configuration operation; it is not user consent.
5. With an authorized test account, separately verify consent, scoped tool listing, one benign read, refresh, and revocation. Confirm denied scopes and tenant policies are enforced. Until those checks are run, retain the limitation in the support evidence.
6. Update catalog validation, provider visibility, guide, and page integration tests for material changes. Cover custom URLs, regions, manual authentication, optional grants, cancellation, and public discovery without saved credentials where affected. Regenerate API types if the schema changes, and run the relevant backend/frontend checks.
7. Update this dated matrix and counts when records or evidence change. Do not replace an earlier failure with a success from a different endpoint, scope bundle, callback environment, or code version without making the distinction clear.

### Account verification checklist

For each account-based service, record the endpoint/region, test-account role and plan, chosen method, and granted scopes without retaining secrets:

- [ ] Consent completes with the intended account and resources.
- [ ] Tool listing succeeds and reflects the selected permissions.
- [ ] One benign account read returns the expected data.
- [ ] Omitted or denied optional permissions remain unavailable.
- [ ] Expiry and refresh behavior work, including external renewal for manual tokens.
- [ ] Disconnect/revocation prevents subsequent authenticated access.

For public services, **Check connection** deliberately avoids saved credentials and stores no account credential. It reports discovered tools; zero tools is reported explicitly. A successful public check must not be shown as a connected vendor account.
